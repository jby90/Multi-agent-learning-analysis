# 同事维护版本选择性合并总结

## 1. 合并原则

本次没有使用同事提供的 `source_package.zip` 整体覆盖当前工程，而是先对同事维护版、原始基线和当前并行协同版进行三方比较，再选择性移植仍有价值的修改。

原因是同事维护版建立在较早版本上，没有包含当前工程后续增加的并行 DAG、四维审核、确定性裁决、Agent 事件流和新版协同前端。整体覆盖会造成现有能力回退。

## 4. 修改后的工作模式

### 4.1 第一次识别某个误区

```text
学员回答
→ 模型诊断本轮误区
→ 后端继续围绕该误区确认
→ 专业审核
→ 通过后记录为已探查
```

### 4.2 同一误区再次未掌握

```text
本轮诊断误区
→ 查询知识库误区关系图
→ 过滤非当前领域目标
→ 过滤岗位责任范围外目标
→ 排除已探查目标
→ 确定下一误区
→ 校验模型结果
→ 四维并行审核
→ 展示下一道问题
```

例如，在当前生产域和责任范围允许的情况下，M-01 重复未掌握后可以确定性地转向 M-04，而不是让模型自由挑选任意误区。

### 4.3 内部异常

```text
生成或状态转换异常
→ 保留最后一个已批准产物
→ 清除未完成学习动作
→ awaiting = done
→ outcome = system_error
→ 返回公开提示
→ 重复请求保持幂等
```

## 5. 修改后的效果

### 5.1 鲁棒性

- 生成或状态转换异常不会让会话停在半完成状态。
- 重复点击“下一步”不会重复推进状态机。
- 相同学员回答的重复请求不会重复审计或生成。
- 内部异常类型、状态编号、规则命中和堆栈不会暴露给学员。

### 5.2 可解释性

- 审计记录同时保存本轮诊断误区和下一目标误区。
- 可以说明下一道问题为什么从 M-01 转向 M-04。
- 路由依据来自知识库关系、岗位责任范围和已探查历史，而不是模型自由判断。

### 5.3 确定性与安全性

- 相同证据、责任范围和探查历史会得到相同的下一目标。
- 模型输出与后端路由不一致时安全拒绝。
- 专业审核重生成问题时不能改变已经确定的诊断和路由结果。

### 5.4 对现有并行架构的影响

- 保留三路资源并发准备。
- 保留四维并行审核。
- 保留确定性审核裁决器。
- 保留 R-02、R-03 定向争议处理。
- 保留 Agent 实时事件流、协同舱和角色动效。
- 正常学习流程和前端接口保持兼容。

## 7. 结论

本次合并保留了同事维护版中有价值的异常兜底和确定性误区关联能力，同时避免旧源码、旧前端、旧评测结果和旧文档覆盖当前并行协同版本。

最终结果不是在当前系统上打兼容补丁，而是把两项能力重新接入现有的学习契约、并行审核、确定性裁决、事件流和领域隔离机制中。
