# 诊断路由修复方案批准指令

**裁决：批准实施，按下列条件冻结。**

采用“5题基础前测 + 每会话最多2道固定诊断探针 + 确定性知识点计划”。本次只修复诊断与知识点路由，不改21条状态转移、R-01～R-06、A选择性辩护、B误区关系选靶、Text2SQL、SQL沙箱和T17降阶机制。

## 一、必须追加的条件

1. **探针必须同时解决知识点可达性和难度定标。**
   - 现有5道前测已覆盖的5个知识点，各补1道应用级校准探针；
   - 现有前测未覆盖的5个知识点，各配置基础级、应用级固定探针；
   - 每次最多展示2道；题干、答案、误区映射全部冻结，不由LLM生成。

2. **生产路由必须完全确定、可审计。**
   - 排序顺序：明确前测/探针错题证据 → 必须补足的前置知识 → 岗位先验薄弱点 → 后续培养扩展点；
   - 同级按知识依赖和配置顺序排序；
   - 生产会话读取 `knowledge_point_plan` 中首个待训练项，不再读取 `blind_spots[0]`；
   - 正式评测不得直接传入 `knowledge_point` 或 `template_id`。

3. **每个计划项必须记录：**知识点、掌握状态、证据来源、证据ID、优先级、初始难度、路由理由和前置知识。

4. **难度规则：**
   - 基础题/基础探针答错 → 基础档；
   - 基础层通过、应用校准探针答错 → 应用档；
   - 应用档学习后答对并满足升档规则 → 生成进阶档资源；
   - 正确回答不得被标记为盲区，`keep`、`step_up`、`step_down`均须有真实交互证据。

## 二、实施顺序

1. 先写失败测试，固定当前不可达基线；
2. 增加固定探针与知识依赖配置；
3. 实现纯确定性的 `DiagnosticRouter`；
4. 接入 `DiagnosisAgent`，输出结构化 `knowledge_point_plan`；
5. 接入生产会话和前端“补充诊断/路由原因”展示；
6. 跑非live全量回归、第二域回归；
7. 跑真实路由门禁；
8. 门禁通过后，再运行新版正式50题两轮。

## 三、验收门禁

- 10个核心知识点真实路由可达：**10/10**；
- 永久不可达知识点：**0**；
- 每次知识点选择均有可追溯证据：**100%**；
- 正式50题中的强制知识点/模板注入：**0**；
- 旧50题强制模式仅保留为内部模块回归，不计入正式三指标。

**批准结论：按本指令实施，不再调整总体方案。**
